# switchboard

A map of the repos under `~/workspace` and the Claude Code sessions running in them (`scan.py`, `serve.py`,
`index.html`), a task list (`tasks/`), and `room/`: a mailbox that lets sessions on several hosts message each other.
README.md describes all three; read its Room section before changing `room/`.

## Working here

- `graph.json`, `graph.js` and `vault/` are generated by `scan.py`: never edit them by hand.
- `tasks/tasks.md` and `tasks/reviews.json` are written by the Tasks tab and hold the owner's own tasks: they are
  gitignored (the repo is public). Never commit them.
- Repos keep TODO files in the format of `tasks/TODO_FORMAT.md`.

## room/

- **Two install channels.** The hosts in cc-menubar's config (Local, RTX, MS) get `room.py` from `room/deploy.sh`,
  which also reinstalls the hooks; MS also gets `room_server.py` (`deploy.sh --restart` restarts it). Everyone else
  installs the PyPI package `switchboard-room` (`room join` to set up, `room update` to upgrade). After changing
  `room.py`, run `room/deploy.sh` so the own hosts match.
- **Stdlib only, Python 3.9+.** The server on MS runs under `/usr/bin/python3` 3.9.
- **Hooks are the hot path.** `room hook <Event>` runs on every tool call: no argparse or heavy imports on that path,
  print nothing unless there is something to deliver, and never raise (the room being down must not disturb a session).
- **Claude sessions read the output.** The session-start hint, `room help`, and the text printed after `send`,
  `listen` and `wait` are instructions to other sessions: keep them short and exact. The `COMMANDS` table in `room.py`
  builds both the argparse parser and the grouped `room help`; add a command there, in the right section.
- **Server and clients upgrade separately.** The server changes when MS is deployed; PyPI clients upgrade whenever
  their owner gets to it. A new server must work with older clients, and a new client with an older server (someone
  else's `room serve`). New fields are optional on both sides.
- **Releases.** Only for changes worth one; small fixes are committed and deployed, and ship with the next release.
  To release: bump `__version__` in `room/room.py` (the workflow refuses a tag that doesn't match), commit,
  `room/deploy.sh`, then `git push origin main && git tag vX.Y.Z && git push origin vX.Y.Z`.
  `.github/workflows/publish.yml` publishes with PyPI trusted publishing; no token is stored. PyPI's index can lag a
  minute behind.
- **Test against a throwaway server, never the live one.** Start one on a spare port with a scratch database and give
  each test client its own scratch `HOME` holding `.config/switchboard/room.json`:
  `ROOM_TOKEN=tt python3 room/room_server.py --host 127.0.0.1 --port 18770 --db <scratch>/r.db`.
  Calls to the live server with made-up session ids create real rows in `room who`. A scratch `HOME` also keeps
  `install-hooks` and the session lookup away from the real `~/.claude`.
- **Never let a test run the real `room update`:** it upgrades a real environment. The `COMMANDS` table holds function
  objects, so stubbing a module attribute is not enough; swap the stub into the table too.
- **Schema changes:** back up the database on MS first
  (`sqlite3 ~/.local/share/switchboard/room.db ".backup …"`), and migrate in `Room.__init__` (see the `version` column).
